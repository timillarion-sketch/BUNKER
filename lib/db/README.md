# @workspace/db — схемы и миграции

## Процесс изменения схемы

Изменения схемы — ТОЛЬКО через `drizzle-kit generate` + `migrate`:

```bash
pnpm --filter @workspace/db run generate   # создать миграцию из изменений schema/*.ts
docker compose up migrate                  # применить новые миграции (сервис в compose)
```

`drizzle-kit push` — только для локального прототипирования, НЕ для применяемых
изменений: `push` создаёт объекты в БД напрямую, но не пишет записи в
`__drizzle_migrations`, из-за чего журнал миграций дрейфует от реальности
(это уже случалось: миграции 0005–0018 были применены через push и их пришлось
вносить в журнал вручную).

Правила:

- После правки `src/schema/*.ts` всегда генерировать миграцию, а не пушить.
- SQL-файлы миграций в `drizzle/*.sql` и снапшоты в `drizzle/meta/` — часть
  истории, коммитить вместе со схемой.
- Если состояние БД и журнала разошлись — сначала восстановить целостность
  журнала, потом продолжать.

## Журнал миграций — боевая схема `drizzle`

Боевой журнал миграций — таблица `drizzle.__drizzle_migrations`. Её читает и
пишет рантайм api-server (`migrate()` при старте контейнера, см.
`artifacts/api-server/src/index.ts`), и с ней же работает CLI: `drizzle.config.ts`
явно задаёт `migrations: { schema: "drizzle" }`, чтобы команды
`generate`/`migrate`/`push` не полагались на дефолты инструментов.

`public.__drizzle_migrations` — legacy-таблица от старой настройки, рантаймом
НЕ используется. Переименована в `public.__drizzle_migrations_legacy_unused`
(переименование обратимо: `ALTER TABLE ... RENAME TO "__drizzle_migrations"`);
не удалять без явного подтверждения.
